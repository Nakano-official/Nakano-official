### [takeover](https://github.com/Nakano-official/takeover) — 大学の障がい学生支援室の業務システム

**私自身がこの支援室のノートテイカーです。** 資料を読んで課題を見つけたのではなく、
働きながら毎回そこで詰まっていた欠員補充が、そのまま出発点になりました。

テイク業務は常に2人体制で、1人欠けたら必ず誰かが入らないといけません。
それなのに欠勤の連絡は Google Classroom への投稿で、生徒ロールの投稿は他の学生へ通知が飛ばない。
本文はバナーに出ず、イベント投稿に埋もれる。**自分で見に行かないと気づけない**仕組みでした。
気づいた職員が人材プールの表を目視で追い、候補者へ一人ずつ電話をかける。
その間、支援を受ける学生の側では、埋まるかどうか分からないまま授業が近づいてきます。

**届かないことが原因なら、届くようにするのが先だ**と考えました。
欠勤が登録された時点でシステムが候補を自動で抽出し、Google Chat で本人たちへ直接届ける。
最初に承諾した人で確定させ、そこに職員を介在させない。
候補が0人でも締切を過ぎても、宙に浮かせず必ず決着をつけて職員へ引き継ぐ。
**誰かが気づくのを待つ状態をなくすこと**が、このシステムの目的です。

要件は支援室と話しながら固めました。その過程で、隣にあったもう一つの手作業——
勤怠データとカレンダーの目視照合——も自然と話題に上がり、土台が重なっていたので
スコープに入れています。目の前の依頼だけを実装して終わりにしない進め方をしました。

個人情報は学内 Google Workspace の中で完結させ、外部のDBやサービスへ出しません。
要件ヒアリングから設計・実装・職員向けマニュアルまで担当し、
2026年9月の授業開始日に本番投入することを目標に進めています。

Google Apps Script / Google Workspace（Chat・Sheets・Forms）

### [Loop-Engine](https://github.com/Nakano-official/Loop-Engine) — プログラミングをせずにシステムを作る実験

コードを1行も書かず、要件を書くだけでシステムが出来上がるか。それを試している最中の実験基盤です。
目指しているのは、人間に残る仕事が「要件を書く」と「ループが詰まったときに答える」の2つだけになる状態で、
しかもそれが**題材を選ばずに成り立つこと**。そこにはまだ届いていません。

この形にすると、最初に「テストが通りました」という報告が壁になります。
人間がコードを読まないのだから、実装した本人が合格を宣言する構造では、誰も何も確かめていないのと同じです。
そこで、仕様と受け入れ条件を作るプランナー、関門を適用するランナー、隔離環境で実装するソルバーの3つに分けました。
真ん中のランナーは AI ではなく普通のプログラムです。関門の値打ちは判断しないことにあるので、
「惜しい」で通す余地をコードのどこにも置いていません。

題材にはインクリメンタルゲームを使っていますが、ゲームを作りたいわけではありません。
手計算した期待値と突き合わせられること、経過時間0や負の値といった異常系が自然に出てくること——
検証しやすさで選んだ題材です。目的は題材の側ではなく、題材を入れ替えても壊れない仕組みの方にあります。

ここまでで、要件ファイルを1枚置いて放っておけば10ステップが緑になり、成果物が起動するところまでは動きました。
ソルバーをローカルの Qwen3.5-9B（RTX 2060 6GB）に差し替えても、11ステップすべて1回の試行で通っています。
ただしこれは「同じ品質のものが出た」という話ではありません。分かるのは関門を通ったかどうかだけで、
実装の良し悪しはこのループのどこでも測っていないからです。

そのことは、うまくいかなかった run 7 がはっきり示しました。10ステップ全緑・42テストで出来上がったゲームは、
1クリックも受け付けませんでした。初期資源はゼロ、生産レートは 0/s、購入ボタンは初回フレームから無効。
どのステップも間違っておらず、部品はすべて正しく、全体だけが死んでいます。
原因は要件ファイルでした。初期状態も、最初の資源をどう得るかも書かれておらず、プランナーは書かれたとおりに実装しただけです。
**コードを書かずに済ませた分、要件を書く側に技術が要る。**
プログラミングをしないシステム開発で次に何が要るのかが、ここで初めて具体的に見えました。

いま取り組んでいるのは、その穴を関門の側で塞げるかどうかです。
ステップごとの受け入れ条件では「新規ゲームから資源を増やせる操作列が存在する」といった全体の性質を誰も持てないので、
そこに届く関門を設計できるか。あわせて、Python と pytest に結合していた検証手段を切り離すため
ランナーに TypeScript を教えました。次はこれで一周させ、新しい関門が本当に効くかを実測します。
題材を変えて回すのは、まだ同じ題材の2本目という段階です。一般性の測定はその先にあります。

Python / WSL2 ・ ランナーは標準ライブラリのみで書いています

### 履修登録支援 AI チャットボット — 履修要項データ設計・整備

龍谷大学プロジェクトリサーチのチーム開発（学生5名・2026年5月から進行中）。
履修要項という非構造の文書を、**卒業要件の判定を機械的に計算できる形**に
構造化するところを担当しています。

6課程＋リベラルアーツ分を1セットとして、入学年度ごとに3学年分（2024・2025・2026年度入学）の
YAML を、原典およびシラバスと照合しながらゼロから作成しました。
入学年度が違えば配当年次も要件枠も変わるため、コホートごとに別のデータとして持ちます。
データを入れながらスキーマの不備を設計側に差し戻し、仕様の全面改訂まで持っていきました。

直近では、自分が出した22件の修正を全件差し戻しています。
2026年度のシラバスと突き合わせて直したのですが、このデータが持つ配当学期・配当年次は
**入学年度で決まって動かない事実**で、その年度に実際どう開講されるかとは別の層の話でした。
照合する先を間違えていたことになります。
科目ナンバリングの配当年次表記まで遡って一件ずつ裏を取り、全件を元の値へ戻しました。

AI が履修相談に正しく答えられるかは、この層が正確かどうかで決まります。
（開発中・組織リポジトリのため非公開）

### HATOBA — フロントエンド担当

賞味期限間近の食材を使って、スーパーのイートインを大学生向けの「夕食食堂」に変える提案です。
店員が値引き商品を撮影すると AI がメニューを提案し、材料費・人件費・販売価格はコード側で計算。
学生はアプリで当日のメニューを見て、席のバーコードから注文する——という流れで、
**スーパーの若年層の取り込み・学生の食費・フードロスを同時に解く**ことを狙いました。

龍谷大学スマートライフハッカソン（平和堂 × ソフトバンク・2026年6〜7月）で **2位**。
6人チームでの開発で、フロントエンドを担当しました。

Next.js / TypeScript / Gemini API ・ [リポジトリ](https://github.com/shimizu-kiichi/HATOBA)
